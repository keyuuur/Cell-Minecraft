# Build a Living Cell — LLM Project Handoff

Last updated: 2026-07-21

## 1. Project purpose and classroom audience

**Build a Living Cell** is a bounded, Minecraft-inspired formative Biology game for first-time ninth-grade learners using school iPads in landscape. Students build a plant cell, inspect the visible contribution of each required component, and restore the cell after a reduced-water-availability challenge. It is not comprehensive Unit 1 mastery or an infinite sandbox.

## 2. Authoritative curriculum sources and Unit 1 boundary

Curriculum authority, in order:

1. `Biology Games/BIOLOGY CONTEXT/BIOLOGY_CONTEXT_INDEX.md`
2. `Biology Games/BIOLOGY CONTEXT/[SHARED] 2025 Unit 1 Notes.pptx`
3. The shared Unit 1 assessment and study-guide bundle in `Biology Games/BIOLOGY CONTEXT`
4. The approved implementation plan

Required structures are exactly: cell wall, cell membrane, cytoplasm, nucleus, ribosomes, mitochondria, chloroplasts, and large central vacuole. The nuclear membrane appears within the nucleus visual but is not separately built or scored.

Out of scope: ER, Golgi apparatus, lysosomes, centrioles, vesicles, cytoskeleton, peroxisomes, osmosis terminology, hypertonic/hypotonic conditions, plasmolysis, ATP-transfer detail, limiting factors, equations, and Unit 2 reaction content. Drought is described as a homeostasis challenge, not as the plant's internal negative-feedback loop.

## 3. Locked product and technical decisions

- Public title: **Build a Living Cell**. Public repository: `Cell-Minecraft`.
- Mission duration: 15 minutes of active, visible gameplay. Pauses, hidden tabs, reload recovery, and orientation interruption do not consume active time.
- Identity: first name, last initial, and period 1–7; private session and attempt IDs are generated locally.
- Primary target: school iPad in landscape, approximately 1024 × 768.
- Stack: Vite, React, TypeScript, Babylon.js, Zustand, IndexedDB, Google Apps Script/Sheets, and Vercel.
- React owns screens and HUD; Babylon owns the stable scene and frame loop; pure TypeScript owns rules, scoring, and serializable state.
- The integrated route will use `VoxelMissionSnapshotV1` as its sole mutable gameplay authority. `MissionState` remains a derived compatibility projection for scoring, HUD, and submission boundaries.
- Integrated contract versions are game `0.2.0`, save schema `3`, and submission contract `2`. The preserved laboratory route remains explicitly game `0.1.0`, save schema `2`, and submission contract `1` until it is replaced atomically.
- Active/practice V2 prototype saves will be detected but will not be spatially migrated after the V3 persistence flow is wired. The UI will offer diagnostic export and a fresh start; locked or queued V2 results remain eligible for bounded delivery compatibility.
- Data Safety uses a non-destructive IndexedDB upgrade of the existing `build-a-living-cell` database from database version 1 to 2. The final local boundary retains `saves` as a legacy quarantine and adds per-attempt `attempts`, `meta`, leased `submissionQueue`, and `receipts`; the upgrade creates missing stores but never spatially migrates or rewrites legacy records.
- `SaveEnvelopeV3` stays frozen. A persistence-only `AttemptRecordV1.storageRevision` orders timer, settings, hint, and delivery writes that can change without a mission revision. Identity matching is normalized only in memory after entry; no low-entropy student identity index or digest is persisted locally.
- New Student clears the active pointer and visible identity while preserving attempts and pending delivery. The separate teacher-device reset requires the exact typed confirmation and clears every local store; it cannot retract a request already accepted remotely.
- Resume is restricted to the current active-attempt pointer and must atomically verify the entered normalized identity, resume eligibility, exact-one/corruption conditions, and pointer update. A hidden prior attempt must not become searchable merely because a later student enters the same limited identity tuple.
- V2 local queue and receipt keys are contract-namespaced so legacy V1 receipt cleanup cannot overwrite or delete a V2 result with the same raw attempt ID. Malformed V2 attempts/queues are quarantined and surfaced as blocked recovery, never silently filtered or mislabeled as legacy.
- One strict shared queue validator owns both legacy V1 and staged V2 read/replay boundaries. It validates the complete payload shape, canonical score, namespaced key/value correspondence, and contract classification; corrupt or wrong-key work fails closed and remains recoverable.
- Only an exact runtime-validated server receipt can settle and delete a queue entry. The shared receipt validator requires exact fields, a matching attempt ID, a parseable server timestamp, and status-consistent error data. Client transport/protocol exceptions never fabricate terminal receipts. Active-time and hint counters are monotonic across every mission revision, and submission-status changes occur only in dedicated atomic queue/receipt operations.
- A locked grade may be hidden or replaced only after its exact matching submission is durably queued or an exact matching terminal receipt is stored. New Student, reset epochs, late saves, and late replay work cannot discard an accountable locked result.
- Contract-V2 persistence, proxy logic, and Apps Script code remain parallel and unwired while the ordinary `/` route stays V2/V1. The future backend cutover is atomic after local parity and adversarial tests; runtime code may verify but may not create, repair, migrate, or silently rebind the existing school-owned Sheet.
- Fixed `24 × 24 × 12` chamber, typed occupancy data, batched/instanced boundary visuals, broad placement zones, and no general chunk engine.
- Integrated prefab safety is three-dimensional and future-aware: each prefab has an explicit occupied height; placement must preserve front-reachable interaction clearance and player egress, avoid continuous player-body overlap, and leave at least one completable arrangement for every unplaced required prefab.
- The integrated scene rebuilds two derived world queries from the fixed template plus `VoxelMissionSnapshotV1`: the visible render world excludes hidden prefab proxies, while collision/raycast queries include height-aware proxy cells mapped back to their semantic prefab owner. Neither query is persisted or becomes a second gameplay authority.
- The approved presentation target is a bright, bounded voxel construction yard around the fixed chamber. First-person walking and drag-look, a center crosshair, an original visible builder pick, ray-targeted mining, a physical pickup, a nine-slot hotbar, and target-based placement are required gameplay verbs.
- The first voxel checkpoint is an isolated, non-scoring proof route. It does not collect identity, run the graded timer, write IndexedDB mission state, submit results, or alter the existing verified mission state.
- Eight visible function-evidence events must be earned in the chamber. Opening Overview never awards function points.
- Corrections restore full credit; hints do not deduct points; impossible placement is blocked immediately.
- Integrated completion is a two-step evidence boundary: the recovered Overview records final-stability evidence but does not lock or submit the attempt. Only an explicit final Submit may freeze the canonical mission and grade, and `SaveCoordinator` must durably save that locked snapshot and matching V2 queue entry as one finalization boundary before Results, New Student, fresh attempt, or practice controls become available. Once locked, voxel commands, player movement, hotbar changes, timer changes, and later saves are no-ops for that graded attempt.
- Rubric: boundary 15, required structures 30, placement/context 15, activation/functions 20, drought recovery 15, final stability 5.
- Dedicated teacher-owned Sheet with append-only raw submissions and a derived best-results view.
- No multiplayer, combat, infinite terrain, crafting tree, accounts, leaderboard, App Store build, PWA, advanced organelles, or third-party analytics.
- The project is independent and uses original procedural visuals. It does not copy Minecraft branding or assets.
